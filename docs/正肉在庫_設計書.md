# 正肉 仕入・在庫管理 設計書（予約システム追加機能）

作成日：2026-10-26　対象：`reservation_system`（Flask＋SQLAlchemy、SQLite／Render上はPostgreSQL）

---

## 1. 基本方針

| 方針 | 内容 |
|---|---|
| **ロット（塊）単位で管理する** | 正肉は「1本・1ブロック」で仕入れて捌くため、1ロット＝1行で、預け→納品→商品化→使い切りまで追いかける。個体識別番号もロットに紐付ける（牛トレーサビリティ法の表示義務への対応）。 |
| **業者預けは「仕入」に入れない** | 伝票未発行の段階はまだ麒麟屋の資産ではない。月次の仕入・棚卸には含めず、画面では「業者預け」として別枠で見せる。 |
| **仕入は伝票の日付で計上** | 今期仕入＝伝票日付が当月の仕入伝票の合計。納品日と伝票日付がずれた場合も伝票を正とする。 |
| **履歴は消さずに積み上げる** | 在庫アプリ（inventory_system）と同じ考え方。状態の変更はイベントとして1行ずつ記録し、「いつ・誰が・何を」を必ず残す。 |
| **確定した月は締める** | 棚卸と原価を確定したら、その月の数字はロックする。翌月の「前繰」は前月の確定棚卸から自動で引き継ぐ。 |

## 2. ライフサイクルと状態

```
 ① 業者預け        ② 納品・伝票発行     ③ 捌き・商品化        使い切り
  held      ──→    received     ──→    processed    ──→    consumed
  (伝票なし)        (伝票あり・原料)      (スライス等の商品)
     │
     └─→ cancelled（買付取消）
                                        ④ 月末棚卸 ─→ 月次締め（原価算出）
```

| 状態 | 意味 | 月次計算での扱い |
|---|---|---|
| `held` 業者預け | 買付約束済み・業者の冷蔵庫で保管中 | 仕入にも棚卸にも**含めない** |
| `received` 納品済み | 店に入り、仕入伝票が発行された原料 | 仕入に計上／棚卸の対象 |
| `processed` 商品化済み | 捌いてスライス・仕込み品になった | 棚卸の対象（商品化後の重量で数える） |
| `consumed` 使い切り | 店内に残っていない | 棚卸の対象外 |
| `cancelled` 取消 | 買付約束が取り消された | 対象外 |

**meat_menu_map（メニュー → 部位の対応）**

出数（POSの販売数）を部位に結び付けるための表。1つの部位が複数メニューに使われる（例：ウデモモ → 赤身・上カルビ・肉寿司）ため、1人前のグラム数を持たせる。

| 列 | 型 | 説明 |
|---|---|---|
| id | PK | |
| menu_name | TEXT NOT NULL | マジレジの商品名 |
| part_id | FK → meat_parts | |
| grams_per_serving | REAL NOT NULL | 1人前の使用量（g） |
| UNIQUE(menu_name, part_id) | | 盛り合わせは部位ごとに複数行 |

1人前の基準（2026-10-26 確認）：**単品（正肉）90g、内臓 100g**。盛り合わせ等はメニューごとに細かく決まっている。

- 単品は部位の分類（meat_parts.category）から基準グラムを自動で入れ、例外だけ直す。
- 盛り合わせは「メニュー × 部位 × グラム」を1行ずつ登録する（例：特選盛り合わせ → ウデモモ 60g・トモバラ 60g・クラシタ 60g）。
- 月次締めの時、マジレジの出数の中に**この表に無いメニュー**があれば一覧で警告する（新メニュー・名前変更の登録漏れ防止）。

加工業者ごとに品名の付け方が違う（「シンタマ」と「芯玉」、「中バラ」と「牛中バラ」等）ため、読み替え表を持つ。

| 列 | 型 | 説明 |
|---|---|---|
| id | PK | |
| processor_name | TEXT | 加工元（空欄なら全業者共通） |
| label_name | TEXT NOT NULL | ラベル上の品名（正規化：全角統一・「牛」「和牛」の接頭語を除く） |

**部位のまとめ方の考え方（2026-10-26 決定）**：同じ商品にどちらを使うか決まっていない部位（ウデとモモ → 赤身・上赤身）は、1つの部位「ウデモモ」にまとめて原価を出す。使い道を追えないものを分けても数字の正確さは上がらないため。ただし細かい部位名（内モモ・シンタマ・トモサンカク・ランイチ 等）もロットごとに残しておき、仕入単価や歩留まりの違いは後から見られるようにする（入力の手間は増えない：写真から自動で入る）。

初めて見る品名は、登録画面で部位を選んでもらい、その選択をこの表に自動で追加する（次回からは自動で部位が入る）。

## 4. 計算式

```
今期使用分（円） ＝ 前繰 ＋ 今期仕入 － 期末棚卸
原価（円/出数）  ＝ 今期使用分 ÷ 出数
```

- **前繰**：前月の `meat_stock_count_lines` の合計（確定済みのもの）。システム導入月だけは手入力（在庫アプリの「前期繰越」と同じ扱い）。
- **今期仕入**：`meat_lots` のうち、紐付く伝票の `slip_date` が当月のものの `amount` 合計。業者預け（held）は入らない。
- **メニュー別の原価**（1部位を複数メニューで使う場合）：部位の使用分を「出数×1人前g」の比で配分する。
  `メニューの原価 ＝ 部位の今期使用分 × (そのメニューの出数×g) ÷ Σ(出数×g) ÷ そのメニューの出数`
- **ロス率**：実際の使用量と理論使用量の差。盛り過ぎ・歩留まり悪化・廃棄の早期発見に使う。

### 5-4. 月末棚卸（`/meat/count/2026-10`）

- 冷蔵庫を歩く順（sort_order）に、店内にあるはずのロットを並べて表示 → 計量した重量を入力。
- 一覧に無い塊はその場で追加、見つからないロットは「無し」を押す（→ consumed）。

### 5-6. ラベル写真の読み取りと個体情報の照会

```
 スマホで撮影 ─→ 予約システム ─→ Claude API（画像を読んでJSONで返す）
                     │                 重量・個体識別番号・賞味期限・部位名
                     ├─→ 個体識別情報検索サービス（家畜改良センター）
                     │                 出生日・と畜日・雌雄・生産者 → 月齢を計算
                     ▼
              入力欄に自動で入った状態で表示 → 人が確認して「登録」
```

```
┌──────────────────────────┐
│ ＋預け（目利き）  フード      │
├──────────────────────────┤
│ [ラベル写真]  ✓ 読み取り完了  │
│ 部位     ウデモモ        ▼   │
│ 重量     8.82 kg              │
│ 個体識別 1234567890  ✓照会済 │
│ 賞味期限 2026-11-08           │
│ 単価     4,200 円/kg          │
│ 金額     37,044 円（自動）    │
├──────────────────────────┤
│ 生産者   ○○牧場（佐賀県…）   │
│ 月齢     31か月　メス 黒毛和種│
├──────────────────────────┤
│ [登録して次の1本]   [登録]   │
└──────────────────────────┘
```

**写真の読み取り（Claude API）**
- スマホのカメラで撮った写真を予約システムのサーバーに送り、Claude API（`claude-opus-5-5`）で読み取る。Structured Outputs（`output_config.format` に JSON スキーマを指定）で、必ず決まった形の JSON が返るようにする。
- 返す項目：重量kg・個体識別番号・賞味期限・ラベル上の品名・読めなかった項目のリスト。
- **自動で保存はしない**。読み取った値は入力欄に入れるだけで、人が見て「登録」を押す。読めなかった項目は黄色で表示する。
- 費用の目安：写真1枚あたり約5〜15円（長辺1,600pxに縮小。出力と思考の分を含めて見直し：2026-10-28）。月100枚で約500〜1,500円。費用はClaudeの月額契約とは別に、API利用料として従量で請求される（Anthropic の API キーが必要）。
- **導入は保留（2026-10-28 決定）**：まず手入力で使い、手数が大きいと感じたら API キーを設定して写真の読み取りを使い始める。キーが無い間は画面に「未設定・手入力で登録できます」と出るだけで、他の機能はすべて使える。
- ラベルのデザインは屠畜・加工業者ごとに違うが、決まった位置の文字を拾う方式ではなく、AIが「どれが重量か・どれが賞味期限か」を意味で判断して読むため、業者ごとの設定は不要。
- 取り違えやすい項目はプロンプトで明示的に区別させる：正味重量と総重量（風袋込み）、賞味期限と加工日・包装日、個体識別番号と荷口番号・ロット番号・JANコード。
- **荷口番号**：複数頭の肉をまとめた包装では、個体識別番号の代わりに荷口番号が表示されることがある。荷口番号は家畜改良センターでは照会できないので、`number_type`（個体識別番号／荷口番号）を返させ、荷口番号のときは照会せず「業者に個体を確認」と表示する。
- 読み取りの検査：個体識別番号は10桁の数字か、賞味期限は今日より後か、重量は部位ごとの常識的な範囲か（例：0.5〜30kg）。外れたら黄色で表示。
- 写真のコツ（画面に表示）：真空パックの光の反射を避けて斜めから撮る、ラベル全体を枠に入れる。
- 導入前に、業者ごとに実物のラベル写真を数枚ずつ集めて読み取り精度を確かめる。

**実物ラベル6枚での読み取り確認（2026-10-26）**

一ノ瀬畜産・東和食品・JA全農みえミートの3社。分かったこと：

- **1枚の写真に複数のラベル**（箱を積んだ状態）、**1枚のラベルに複数の塊**（みえミートの「牛セット」は1箱3本）がある → 読み取り結果は「塊の配列」で返し、1塊＝1ロットとして登録する。セットはシリアル（セット番号）でまとめて表示する。
- **重量が2つある**：「重量」（11.14kg）と「取引値」（11.1kg、0.1kg未満切り捨て）。両方を保存する。
- **3社ともGS1-128バーコードを使っている**：バーコード下の数字に `(251)個体識別番号`・`(3102)正味重量`・`(11)加工日`・`(21)シリアル` が入っている。文字と同じ値が入っているので、読み取った文字との照合（食い違いの検出）に使える。賞味期限はバーコードに入っていないので文字から読む。
- 日付は「26.10.25」「26.9.11」のように年が2桁 → 2026年として扱う。
- 写りが悪いもの（奥の箱で小さい・ぼやける、紙が破れて番号が一部隠れる）は、読めない項目を空欄で返させ、人が補う。同じ個体の別ラベルや、バーコード下の数字から補えることも多い。
- 業者のラベルにバーコードが付いている場合、重量や賞味期限が中に入っていることがある。実際のラベルを見て、使えるなら併用する。

**個体識別番号の照会（家畜改良センター）**

> **実装の現状（2026-10-28）**：社長が「利用上の注意」を確認し、仕入れた肉の個体確認のための自動照会に同意。社長の同意のもとで 1680941492 を1回照会し、実際の検索結果ページの作りに合わせて自動照会を実装した（cattle_lookup.py）。目利きの登録時に、未照会の番号だけを1頭1回照会して meat_cattle に保存する（続けて照会する時は1秒あける）。取得できない時は手で転記する欄に切り替える。止めたい時は環境変数 NLBC_AUTO_LOOKUP=0。サーバーは古い暗号方式のため、接続時に SECLEVEL=1 を指定している。なお家畜改良センターは個体識別情報の有料提供も行っている（https://www.id.nlbc.go.jp/pdf/katsuyou_kankei.pdf）。
- 家畜改良センター「牛の個体識別情報検索サービス」には公式のAPIが無いため、サーバーが利用者と同じ手順（利用上の注意に同意 → 番号で検索）で画面を取得し、必要な項目を取り出す。
- 利用上の注意では、牛の個体識別に関する法律の目的以外での利用が禁止されている。仕入れた牛肉の個体を確認・記録する使い方はこの目的に沿うが、照会は登録時の1頭1回だけにし、結果は `meat_cattle` に保存して二度目以降は照会しない。
- サイトの作りが変わると取り出しが壊れる。そのときは「照会できませんでした」と表示し、検索サービスを開くボタン（番号入力済み）で人が確認できるようにする。
- 照会で見つからない番号は、写真の読み間違いの可能性が高いので、番号の欄を赤にして見直してもらう。
- 月齢＝と畜日−出生日。メス・黒毛和種かどうかもここで確認できる（麒麟屋の「黒毛和牛メス牛」の裏付け）。

**写真の保存先**
- Render の無料プランは、サーバーのディスクに置いたファイルが再起動・更新のたびに消える。写真は長辺1,600px程度のJPEG（1枚200KB前後）に縮めて、データベース（PostgreSQL）に保存する。

## 6. 既存システムとの関係

- **予約システムへの追加**：`database.py` の `init_db()` に上記テーブルを追加し、ルートは `meat_` で始まる別ファイル（Blueprint）にまとめて app.py の肥大化を避ける。Render の PostgreSQL にもそのまま作られる。
- **在庫アプリ（inventory_system）**：同じ品目（ウデモモ・クラシタ等）を別に管理している。正肉は本機能へ移し、在庫アプリはドリンク・加工肉・野菜など「数・パック単位」の品目に絞るのが二重入力を避ける形。部位マスタの初期値は在庫アプリの商品マスタ（seed_kirinya_items.py）から移す。
  - **ウインナーは袋の数で、在庫アプリのまま管理する**（2026-10-29 決定）。正肉在庫のグラム表には入れない。使用量の目安：1袋を半分に切ると10本、シャウエッセン単品＝半袋、地鶏/豚/ウィンナー盛り＝4本。
- **出数**：マジレジの商品別売上CSVを月1回取り込む（既存の pos_import は伝票単位のため別機能）。

## 7. 利用者と権限

現在の予約システムは全スタッフ共通のパスワード1つ（`APP_PASSWORD`）でログインする。仕入単価は社内なら誰に見せても問題ない（2026-10-26 確認）ので、**見るのは制限しない**。守るのは「登録・変更」と「締め」。

**第1段階（今：入力は社長だけ）**
- 在庫一覧・ロット詳細（仕入単価・金額を含む）は、予約システムにログインできる人なら誰でも見られる。
- 目利き・納品・捌き等の登録や修正、月次の締めは、**管理者パスワード**（環境変数 `MEAT_ADMIN_PASSWORD`）を入れた時だけできる。誤って数字を変えてしまうことを防ぐため。
- すべての記録に入力者名を残す（meat_lot_events.staff_name 等）。委任後に「誰が入力したか」を区別するため、今から入れておく。
